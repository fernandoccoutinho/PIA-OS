# ADR-008 — Três Dockerfiles autocontidos, não uma cadeia de imagens-base

**Status:** Aceito
**Módulos envolvidos:** 2.11 (Containerização, Deploy e Operação)

## Contexto

A especificação do Módulo 2.11 pede três Dockerfiles (`Dockerfile`,
`Dockerfile.dev`, `Dockerfile.prod`) e, ao mesmo tempo, orienta evitar
duplicação de configuração.

## Decisão

Cada um dos três Dockerfiles é autocontido — builda isoladamente sem
depender de uma imagem intermediária pré-construída — aceitando ~8
linhas de boilerplate repetido (`apt-get install`, `pip install` das
dependências base) entre eles.

## Justificativa

A alternativa (uma imagem-base construída primeiro, com `Dockerfile.dev`/
`Dockerfile.prod` fazendo `FROM pia-os-backend-base:latest`) exigiria um
passo de orquestração extra antes de qualquer build individual — quebra
o fluxo de `docker compose up` de um comando só, e introduz uma
dependência de ordem de build que não existe hoje. A duplicação evitada
pela especificação refere-se a não redefinir *valores de configuração*
(variáveis de ambiente, `Settings`) em lugares diferentes — não a
boilerplate de infraestrutura de build, que é um padrão comum e aceito
em projetos reais com múltiplos Dockerfiles por ambiente.

## Impacto

Uma mudança na versão base do Python ou nos pacotes de sistema
(`apt-get install`) precisa ser replicada manualmente nos três arquivos
— um custo de manutenção real, mas pequeno e infrequente, documentado em
`deploy/README_DEPLOY.md`.

## Alternativas consideradas

- **Multi-stage único com `target:` no Compose** (`docker build --target
  development`): tecnicamente mais DRY, mas não produz os três arquivos
  fisicamente separados que a especificação pede — descartada para não
  divergir da estrutura de arquivos exigida.
- **Imagem-base publicada e versionada** (ex.: `pia-os-backend-base:0.1.0`
  num registry): correta para um pipeline de CI/CD maduro, mas exigiria
  infraestrutura de registry que não existe nesta etapa — fica como
  melhoria futura.
