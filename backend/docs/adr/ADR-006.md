# ADR-006 — CORS usa `CORSMiddleware` do Starlette, não reimplementado

**Status:** Aceito
**Módulos envolvidos:** 2.8 (Segurança Base)

## Contexto

Diferente da validação de host (ADR-005), a especificação do Módulo 2.8
pedia CORS centralizado via configuração — sem exigir que a resposta a
uma violação de CORS seguisse o envelope de erro da API.

## Decisão

CORS usa `starlette.middleware.cors.CORSMiddleware` diretamente,
configurado a partir de `Settings` (`app.security.cors.build_cors_kwargs`)
— não uma reimplementação própria.

## Justificativa

A lógica de preflight (`OPTIONS`), ordem de headers, tratamento de
credenciais e interação com `Vary` é sutil e já vem testada como parte
do próprio FastAPI/Starlette (nenhuma dependência nova). Diferente da
validação de host, uma violação de CORS não é "rejeitada com uma
resposta de erro visível ao servidor" no mesmo sentido — é o *navegador*
do cliente que bloqueia o acesso ao resultado; o servidor processa a
requisição normalmente. Não há, portanto, o mesmo requisito de "log de
violação" que motivou reimplementar a validação de host.

## Impacto

Zero superfície de manutenção extra para a lógica de CORS em si — só a
tradução `Settings -> kwargs`. Nota de segurança documentada:
`CORS_ALLOW_CREDENTIALS=true` nunca deve coexistir com
`CORS_ALLOWED_ORIGINS=*` (o próprio Starlette recusa essa combinação em
runtime).

## Alternativas consideradas

- **Reimplementar CORS manualmente, como a validação de host**:
  descartada — sem o mesmo requisito de logging de violação que
  justificou o esforço extra para hosts confiáveis, o custo de
  reimplementar não se paga.
