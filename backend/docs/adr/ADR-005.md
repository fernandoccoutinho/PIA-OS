# ADR-005 — Validação de host confiável é manual, não `TrustedHostMiddleware`

**Status:** Aceito
**Módulos envolvidos:** 2.8 (Segurança Base)

## Contexto

O Starlette já oferece `starlette.middleware.trustedhost.TrustedHostMiddleware`,
pronto para validar o header `Host`. A especificação do Módulo 2.8 exige
que toda violação de segurança seja registrada no Logger Central e siga
o mesmo formato de resposta de erro do resto da API.

## Decisão

A validação de host confiável é feita manualmente dentro do
`SecurityMiddleware` (`app.security.trusted_hosts.is_trusted_host`), não
via o middleware nativo do Starlette.

## Justificativa

`TrustedHostMiddleware` responde diretamente com uma `PlainTextResponse`
quando rejeita um host — não passa pelos handlers globais de erro
(Módulo 2.7) nem pelo Logger Central (Módulo 2.6). Usar o middleware
nativo violaria a exigência explícita do Módulo 2.8 de que toda violação
seja registrada e de que toda resposta de erro siga o envelope
padronizado.

## Impacto

Uma dependência a menos do comportamento pronto do Starlette em troca de
consistência total com o pipeline de erro/log da plataforma — toda
violação (host, tamanho de payload, Content-Type, rate limit) agora usa
exatamente o mesmo caminho de código para responder e logar.

## Alternativas consideradas

- **Usar `TrustedHostMiddleware` e aceitar a inconsistência de log**:
  descartada — violaria um requisito explícito do módulo.
- **Sobrescrever o handler de `TrustedHostMiddleware`**: o middleware
  nativo não expõe um ponto de extensão para isso; seria necessário
  monkey-patch ou subclasse frágil, mais arriscado que reimplementar a
  checagem (que é simples: comparar o header `Host` contra uma lista).
