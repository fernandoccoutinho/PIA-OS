# ADR-003 — Exceções em middleware chamam o handler global diretamente

**Status:** Aceito
**Módulos envolvidos:** 2.7 (Tratamento Global de Erros), 2.8 (Segurança Base)

## Contexto

`SecurityMiddleware` e `RateLimitMiddleware` (Módulo 2.8) precisam
levantar erros estruturados (`PIAOSException`) quando detectam uma
violação. A expectativa inicial era que `raise` dentro do middleware
seria capturado pelos handlers já registrados via
`app.add_exception_handler` (Módulo 2.7) — não foi o que aconteceu: toda
violação virava um 500 genérico.

## Decisão

`SecurityMiddleware`/`RateLimitMiddleware` capturam `PIAOSException`
internamente (`try`/`except`) e chamam
`app.exceptions.handlers.piaos_exception_handler(request, exc)`
diretamente, retornando a resposta gerada por ele — em vez de apenas
`raise`.

## Justificativa

É uma limitação real do Starlette/FastAPI: `ExceptionMiddleware` (que
despacha por tipo de exceção para os handlers registrados) fica *dentro*
da camada de roteamento; middlewares de usuário (`BaseHTTPMiddleware`,
adicionados via `app.add_middleware`) ficam por fora dela. Uma exceção
levantada num middleware nunca passa pelo `ExceptionMiddleware` — só o
catch-all genérico da `ServerErrorMiddleware` a vê, que não sabe
traduzir por tipo/código específico.

## Impacto

Qualquer middleware futuro que precise sinalizar um erro estruturado
deve seguir o mesmo padrão (capturar e chamar o handler diretamente),
não apenas `raise`. Isso está documentado explicitamente em
`docs/backend/security.md` para não ser redescoberto por tentativa e
erro.

## Alternativas consideradas

- **Responder manualmente com um `JSONResponse` construído à mão dentro
  do middleware**: descartada — duplicaria a lógica de montagem do
  envelope de erro e do logging que `piaos_exception_handler` já faz.
- **Migrar para `Starlette.exception_handler` de nível mais baixo
  (ASGI puro)**: avaliada e descartada por exigir reescrever a pilha de
  middleware inteira só para resolver um caso específico.
